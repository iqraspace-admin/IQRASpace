IqraSpace — Developer Guide

The single entry point for understanding, running, and safely extending every app in this monorepo. Written from a direct review of the current codebase — not from memory of earlier docs, which have in several places fallen behind the code (flagged throughout, and summarized in §22).

1Project Overview

What IqraSpace is, who it serves, and how the repository is shaped.

What the system does

IqraSpace is not one application — it's a small family of independent products that share a brand and a domain, built and run by a single developer/owner. The repo root's CLAUDE.md is explicit about this and the code confirms it: there is no shared package, no shared UI library, no shared types between apps. Each app has its own stack, its own data store (or none), its own CI pipeline, and its own deployment target (a Cloudflare Worker for each web app, Play Console for the Android app).

Quranic Teacher apps/learning

A tutoring LMS for one solo Quran tutor and their students: scheduling, live PDF-based teaching with real-time highlight sync, attendance, progress tracking, curriculum ("lesson plans"), notifications. Requires login. Lives at iqraspace.org/learning.

IqraSpace Quran apps/quran

A free, anonymous-first public Quran reader: Surah/Page/PDF reading modes, audio (per-ayah and whole-Surah), Tajweed coloring, search, bookmarks — all local-only today, no login required. Served as a static export from an assets-only Cloudflare Worker at iqraspace.org/quran. (Its Supplications feature was removed on 2026-10-03; Duas now live in the Flutter app.)

IqraSpace Quran (Flutter) apps/mobile/android

The native Android (and web-capable) counterpart to apps/quran, but a fully separate codebase and data source: Tajweed-colored reading, Listening Mode, Supplications (remote content with a bundled fallback), bookmarks — offline-first via Hive. Distributed through Google Play (closed testing).

Site apps/site

The hand-authored static marketing/info site that owns the iqraspace.org domain root (home, about, mission, explore, duas, contact, FAQ, privacy, terms…), plus one tiny Worker endpoint (POST /api/contact, stored in Cloudflare D1). No framework. /quran* and /learning* are not proxied through it — they are separate Workers bound to more specific routes on the same Cloudflare zone.

2High-Level Architecture

How a request actually gets from a browser to the right app, and how the four apps relate to each other.

Diagram

Solid arrows are live dependencies; dashed ones are optional, build-time-only, or not deployed. The Flutter app calls only two anon-callable Duas RPCs on the Learning Supabase project (published content only) and otherwise stays offline-first.

One connection root CLAUDE.md doesn't mention The R2 audio bucket is documented as apps/mobile/android's "one deliberate exception" to isolation from apps/quran. In the current code, apps/quran also fetches whole-Surah audio directly from that same bucket (its Listening Mode CSP allow-lists https://audio.iqraspace.org, and src/lib/content/listeningAudio.ts builds the same URL scheme, ported from the Flutter app's Dart constants). Nothing is shared code-wise or via imports — both apps independently hard-code URLs to the same public, keyless CDN endpoint — but it means the R2 bucket is now a dependency of two apps, not one. Worth knowing before renaming keys or restructuring that bucket.

Path routing on one Cloudflare zone, traced end to end

A request to iqraspace.org/quran/surah/2:

  1. DNS: the @ and www A records point at the placeholder 192.0.2.1 and are Proxied (orange cloud). The address is never contacted — a Worker route answers first. Worker routes only fire for proxied records, so un-proxying these records takes the site down.
  2. Cloudflare matches the request path against the routes declared in each app's wrangler.jsonc. iqraspace.org/quran* belongs to iqraspace-quran; iqraspace.org/learning* to iqraspace-learning; iqraspace.org/* to iqraspace-site. The most specific pattern wins, so no app proxies to another and the browser never sees a hop.
  3. iqraspace-quran is an assets-only Worker (no script): Workers Static Assets serves dist/quran/surah/2.html directly with html_handling: "drop-trailing-slash" (so /quran/surah/2/ redirects, 307, to /quran/surah/2). Security headers/CSP come from a generated _headers file, not next.config headers().
  4. iqraspace-learning is also a static export, plus a small Worker script that runs only for the dynamic-route URL patterns (run_worker_first): /learning/share/*, /learning/teach/*, /learning/admin/duas/* (minus the fixed sub-pages new, list, activity, categories, categories/new). Details and the safe way to add a route are in §25.
  5. iqraspace-site serves everything else from its own static assets and runs its Worker only for /api/* (POST /api/contact).
  6. www.iqraspace.org/* is bound to a fourth, tiny Worker (iqraspace-www-redirect) that 301-redirects to the apex preserving path and query.

Net effect: three independent Workers, each with its own wrangler.jsonc, build and CI workflow, stitched into one domain by the zone's route table alone. Routing changes are edits to the relevant app's wrangler.jsonc routes (and, for the www host, apps/site/www-redirect) — there is no vercel.json, no Multi-Zones rewrites(), and nothing is hosted on Vercel any more (see §22 for the historical note).

5For a New Developer

A concrete, ordered path using only commands that actually exist in this repo.

  1. Read this document's §2–§4, then skim the per-app section (§6–§9) for whichever app you'll actually touch.
  2. Prerequisites: Node ≥20.9 + npm for the Next.js apps and apps/site; Flutter 3.47.3/Dart ≥3.5 for apps/mobile/android; Wrangler (installed as a dev dependency or via npx wrangler) only if you need to preview/deploy the Workers. Full commands are in §24.
  3. Clone and install only what you need — there's no repo-wide install step: 
    # apps/learning
npm install --prefix apps/learning

# apps/quran
cd apps/quran && npm install

# apps/mobile/android
cd apps/mobile/android && flutter pub get
  4. Configure environment — copy each app's .env.local.example to .env.local and fill in your own Supabase project URL/anon key (learning; for the real backend use the iqraspace-learning project's public URL + anon key from the owner) or Quran Foundation sandbox credentials (quran, only needed if you're touching content sync). apps/mobile/android needs no env file for normal development (only for the release-upload pipeline); to see remote Duas locally pass the two --dart-defines from §27.
  5. Apply the DB schema (apps/learning only, if you need a working backend): 
    npx supabase login
npx supabase link --project-ref <your-project-ref>
npx supabase db push          # applies supabase/migrations/*.sql from repo root
    Or paste supabase/migrations/0001_init_schema.sql into the Supabase SQL editor as a one-time bootstrap, then push the rest.
  6. Run it: 
    npm run dev --prefix apps/learning   # http://localhost:3000
cd apps/quran && npm run dev          # http://localhost:3001 (deliberately different port)
cd apps/mobile/android && flutter run -d chrome   # or a connected Android device
  7. Verify: apps/learning — sign up, confirm a public.users/tutors or students row was created by the DB trigger. apps/quran — reading/search/bookmarks should all work with zero configuration (it's local-storage-only today). apps/mobile/android — the app should boot straight to Home with no login screen.
  8. Run the checks before any change: npm run lint, then npx next typegen && npm run typecheck (both Next.js apps need the next typegen step first on a fresh checkout — see §17), npm run build. For Flutter: flutter analyze and flutter test (what CI actually gates on).
  9. Make a small, safe change — e.g. a copy tweak in one component — and confirm the dev server hot-reloads it and lint/typecheck still pass.
  10. Understand deployment before pushing to main on anything CI-guarded (§16, §25) — the three web apps build with npm run build:cf and deploy to Cloudflare Workers (CI deploy is currently not working; production is deployed manually with wrangler, §25). Flutter is analyze/test-only in CI; release is a separate manual/skill-driven process.
  11. Never apply database changes through CI — migrations are applied by the owner with npx supabase db push from the repo root (§26).

No middleware.ts and no src/app/api routes exist anywhere in this app — it is a pure static export (output: "export", basePath: /learning, trailingSlash handled by Cloudflare's drop-trailing-slash). Adding a new dynamic route means touching four places; the checklist is in §25.

Narrow — there is no UI/E2E suite and the generic npm run test step is still a no-op in CI (--if-present). Known gaps (confirmed against code)

  • Google Drive/Calendar integration — genuinely unconfigured, not faked (see above).
  • Guardian role exists in the DB/type system with no dedicated portal.
  • Highlight sync is page-level for PDFs, not the normalized-coordinate rect/word-level sync the original architecture doc sketched.
  • Student-based one-to-one scheduling (migration 0023) was explicitly flagged in PROGRESS.md as not independently end-to-end tested — and the app now runs on a brand-new, empty Supabase project, so verify booking, recurring-session generation and "Launch Lesson from Today's Sessions" from scratch.

7apps/quran — IqraSpace Quran (public reader)

Free, anonymous-first Quran reader, served as a static export from an assets-only Cloudflare Worker. Its Supplications feature was removed on 2026-10-03 (commit 778bf90); Duas now live in the Flutter app and are managed remotely (§27).

Correcting stale claims in root CLAUDE.md Older revisions of root CLAUDE.md described this app as "Next.js 16 + Capacitor" with cap:sync/cap:open:android scripts and a ci-quran-mobile.yml workflow, and Vercel/Multi-Zones hosting (root CLAUDE.md has since been corrected). The actual native Android app for the Quran reader today is the sibling apps/mobile/android, a fully different codebase.

Content pipeline

Source: Quran Foundation Content API (OAuth2 client-credentials, server-side only). npm run sync:content fetches all 114 chapters / 6,236 verses (Uthmani text) plus translations and writes them to src/content/generated/. This output is deliberately committed to git, not gitignored (so CI never needs live API access, and to respect the API's rate limits). The Quran Foundation licence requires a re-sync at least every 7 days — this used to be manual; the new sync-quran-content.yml workflow now runs weekly (guarded by the QURAN_SYNC_ENABLED repo variable), and if the content changed it opens a PR (it never pushes to main). A second, build-time-only pipeline (generate-search-index.mjs, wired into npm run build) turns that committed content into public/search-index.json for client-side search — no network call, no credentials needed at build time.

Cost-consciousness (hard constraint)

Target is genuinely $0/month at pilot scale: Cloudflare Workers Free (static asset requests are free and unlimited; this Worker has no script, so it never counts against the 100k requests/day Worker quota), Quran Foundation API is free, and all audio streams from external CDNs (cdn.islamic.network for per-ayah, the Flutter app's Cloudflare R2 bucket for whole-Surah) — never through this app's own bandwidth. Static Assets limits to keep in mind: 25 MiB per file, 20,000 files per Worker (dist/quran is currently 4,534 files / 375.8 MiB, largest PDF 14.8 MiB). Explicitly disallowed absent a documented requirement: Kubernetes/microservices, Elasticsearch/Algolia, paid CMS, Redis, self-hosted audio storage. Search's static-JSON approach is a direct product of this rule, not a limitation to "fix" later.

Live-teach highlight sync (apps/learning), traced end to end

This is the most architecturally interesting workflow in the repo — a genuine real-time feature, not a demo.

  1. Tutor opens /teach/[lessonId] → TeachClient.tsx selects a PDF page or ayah.
  2. It broadcasts a "highlight" event with a HighlightState payload over a Supabase Realtime channel named lesson:{lessonId}.
  3. In parallel, it calls lib/sharing.ts's recordHighlight(), which durably writes the same state to the highlighted_content table — this is the architecture's audit trail, independent of the broadcast.
  4. The student's ShareClient.tsx (on /share/[lessonId]) is subscribed to the same channel and updates its view live on receipt. Both sides also use Realtime Presence (channel.track(...)) to show a "connected" indicator.
  5. Because broadcast has no replay, a reloading or late-joining student would otherwise see nothing until the next broadcast — getLatestHighlight() runs a DB catch-up query against the active sharing_sessions row on page load to fix that.

Net pattern: broadcast for liveness, database row for the record — a pattern worth reusing if a similar live-sync feature is ever needed elsewhere.

Notifications (apps/learning)

Plain DB rows, not push/email. All inserts go through a single notify_user() SECURITY DEFINER RPC — direct table inserts are never used — which only allows self-notify or a tutor notifying their own student. The topbar bell reads via a fetch wrapper; its exact refresh mechanism (poll vs. live) was not independently confirmed during this review — check NotificationBell.tsx directly before assuming it's real-time.

20Development Rules & Conventions

  • Apps are independent — verify before assuming sharing. No shared package, types, or UI library exists between any two apps. Cross-app references are always either a deep link (URL) or a public, anonymous endpoint (the Flutter app's two Duas RPCs; the R2 audio URLs), never a code import.
  • apps/quran must stay anonymous-first. Reading, search, audio, and theme/font preferences must never require sign-in. Auth is reserved exclusively for future optional cross-device sync.
  • apps/quran's cost ceiling is a hard constraint, not a suggestion — no paid infra, no unnecessary third-party API dependencies for core reading. The resilience rule is explicit: "reading still works if audio/search/login/analytics are down."
  • apps/mobile/android's isolation from apps/quran is deliberate (different applicationId, no shared code) with exactly one sanctioned exception: the Cloudflare R2 audio bucket, which — per current code — both apps now independently consume (see the callout in §2). Don't casually add a second "exception."
  • RLS is the real authorization boundary in apps/learning, not client-side checks. Any new table needs its own RLS policies (migration 0001's tables shipped with RLS enabled but zero policies — a deliberate deny-by-default placeholder pattern to follow for new tables too).
  • Never reference another RLS-protected table via an inline subquery in a new policy — use or extend the existing STABLE SECURITY DEFINER helper functions to avoid the recursion bug fixed in migration 0004.
  • Admin/super_admin accounts are never created by public signup, by design, enforced server-side in the DB trigger and independently in the Edge Function. Don't add a code path that lets a client specify its own privileged role.
  • Quran content in apps/quran is licensed, cached content — it must be re-synced within the license's cache window (7 days; now automated weekly by sync-quran-content.yml) and must never be modified or redistributed as a standalone product. Don't hand-edit src/content/generated/.
  • Always bump only the +N build number in apps/mobile/android's pubspec.yaml before a real release build; bump x.y.z itself only for an explicit, user-requested version change.
  • Run app-specific commands from inside that app's directory (or with an explicit --prefix) — root package.json only proxies a subset of commands for two of the four apps.
  • Hosting is Cloudflare, not Vercel. Don't reintroduce vercel.json, Multi-Zones rewrites or Vercel env vars. Everything the Next apps need at runtime is inlined at build time.
  • Never claim a Duas text is verified unless a source was checked. Don't machine-translate Urdu, don't invent hadith numbers, don't paste copyrighted Wa Iyyaka text; unverified content stays draft / needs_review (§27).
  • Database changes are manual. CI never runs supabase db push; add a numbered migration under supabase/migrations/ and have the owner apply it (§26).
  • No secrets in docs, repo or the app bundle. Only public values (Supabase URL + anon key) are ever baked into a build.

The Learning dynamic-route Worker — and adding a route safely

Why it exists: a static export can't contain pages for ids that don't exist at build time. apps/learning/worker/index.js + routes.js map four URL families to one placeholder shell each (/learning/share/<id>, /learning/teach/<id>, /learning/admin/duas/<id>, /learning/admin/duas/categories/<slug>), rewriting internally (no redirect) so existing links keep working; the browser still shows the real URL and the client reads the id from window.location. Why run_worker_first is limited to those patterns: the Workers Free plan allows 100,000 Worker requests/day, while static-asset requests are free and unlimited — so the Worker must not run for ordinary pages, JS, images or PDFs. Fixed sub-pages (new, list, activity, categories, categories/new) are excluded with ! patterns.

To add a new dynamic route (e.g. /learning/foo/<id>):

  1. Create the page at src/app/(...)/foo/[id]/page.tsx with generateStaticParams() returning only the placeholder [{ id: "_" }] (look at an existing one such as share/[lessonId]).
  2. In the client component, read the id with src/lib/routeParam.ts / RouteEntry (from window.location) — never from Next's params.
  3. Add the pattern to worker/routes.js (matchDynamicRoute) and a test in worker/routes.test.mjs; list any fixed sibling pages in the static-segment sets.
  4. Add /learning/foo/* (plus ! exclusions for fixed siblings) to assets.run_worker_first in apps/learning/wrangler.jsonc. Missing this makes the URL 404 from static assets.
  5. Add a health-check path in ci.yml if it matters, run npm run test:worker and npm run build:cf, preview with npx wrangler dev --local using a real-looking id, then deploy.

Static Assets limits & free-tier guard rails

  • 25 MiB per file, 20,000 files per Worker's assets. dist/quran: 4,534 files, 375.8 MiB, largest PDF 14.8 MiB — plenty of file-count headroom, watch single big PDFs.
  • Free plan: 100k Worker requests/day and 10 ms CPU per request — the reason Learning auth stays on Supabase and the Worker does nothing but path matching. D1 free: 5 GB, 5M rows read/day, 100k written/day. R2 free: 10 GB, free egress. Limits as understood at the time of the feasibility study — re-check before relying on them.
  • Headers live in generated _headers files (site: security headers + CSP; quran: security headers + CSP allowing cdn.islamic.network/audio.iqraspace.org media and api.alquran.cloud, plus CORS * on /quran/pdf/*; learning: nosniff, Referrer-Policy, SAMEORIGIN, Permissions-Policy and no CSP). Edit them in each app's build script (scripts/build.mjs, prepare-cf.mjs), not by hand in dist/.

How to add or change content

  • Day to day: use the admin UI (/learning/admin/duas, admin/super_admin login). Edit, preview, move through draft → review → published, unpublish/archive; every change is audited with field diffs and can be restored. The app picks up published changes without a release (next version check, ≤ hourly or on pull-to-refresh).
  • Bulk/structural changes use the pipeline (new categories in bulk, re-import of verified texts, schema changes). Pipeline changes only reach production through a new migration applied with supabase db push — and only reach installed apps' fallback data through a new release (--write-bundled).
  • Rules: a published Dua needs Arabic (Arabic script) and an English translation; repeat_count is an integer (1–1000), never free text; hadith_number only where verified; unverified material stays draft/needs_review. The 95 Wa Iyyaka draft stubs have no Arabic on purpose (the book is copyrighted) — an admin must supply verified Arabic. Don't paste the book's text.

Importing Urdu translations

Only populated where a verified source exists: today the Qur'an's ur.maududi edition for Duas that are exactly a whole ayah range (Ayat al-Kursi, the Three Quls, plus 8 draft stubs). Hadith Duas are empty — nothing is machine-translated. Path: fill reports/urdu_translation_template.csv (186 rows) → node import_urdu.mjs filled.csv --source "<citation>" → writes data/urdu_translations.json → node build_canonical.mjs. The importer is strict: it rejects text that isn't Urdu, text that merely repeats the Arabic, and a missing --source. The owner has not supplied a source yet.

Data model & RLS summary

  • duas — slug (unique), title/title_ur, arabic (+ generated arabic_normalized), transliteration_latin/telugu/urdu, translation_en/ur, description, repeat_count, source_type (quran|hadith|mixed|other), source_collection, source_reference, hadith_number, hadith_grade, quran_refs (jsonb), audio_url (https only), status (draft|review|published|archived), verification_status (verified|unchecked|needs_review), review_notes, origin, wyn_ids, sort_order, timestamps and created_by/updated_by.
  • dua_categories; dua_category_map (one canonical Dua shown under several categories, with per-category overrides context_title, context_title_ur, context_note, context_reference, context_repeat_count; deleting a mapped category is RESTRICTed); dua_audit_log (append-only, written by triggers for all three tables).
  • RLS/privileges: anon has no table privileges — only the SECURITY DEFINER RPCs get_dua_content() (consistent snapshot of published Duas in active categories) and dua_content_version() (md5 freshness check). Writes need a signed-in Learning user whose public.users.role is admin or super_admin (helpers dua_role, is_dua_admin, is_dua_staff). Triggers stamp created/updated/published_at and enforce the workflow; no API role can alter the audit log.
  • Counts today: 41 categories, 197 Duas (102 published + 95 drafts), 213 mappings; public snapshot = 30 categories (empty ones omitted) and 102 distinct Duas.
