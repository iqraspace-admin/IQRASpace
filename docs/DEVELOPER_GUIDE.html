IqraSpace — Developer Guide

The single entry point for understanding, running, and safely extending every app in this monorepo. Written from a direct review of the current codebase — not from memory of earlier docs, which have in several places fallen behind the code (flagged throughout, and summarized in §22).

Reviewed: 2026-09-20 4 independent apps, 1 domain Source of truth: current code > existing docs

1Project Overview

What IqraSpace is, who it serves, and how the repository is shaped.

What the system does

IqraSpace is not one application — it's a small family of independent products that share a brand and a domain, built and run by a single developer/owner. The repo root's CLAUDE.md is explicit about this and the code confirms it: there is no shared package, no shared UI library, no shared types between apps. Each app has its own stack, its own data store (or none), its own CI pipeline, and its own Vercel/Play Console deployment target.

Quranic Teacher apps/learning

A tutoring LMS for one solo Quran tutor and their students: scheduling, live PDF-based teaching with real-time highlight sync, attendance, progress tracking, curriculum ("lesson plans"), notifications. Requires login. Lives at iqraspace.org/learning.

IqraSpace Quran apps/quran

A free, anonymous-first public Quran reader: Surah/Page/PDF reading modes, audio (per-ayah and whole-Surah), Tajweed coloring, search, Supplications (duas), bookmarks — all local-only today, no login required. Lives at iqraspace.org/quran.

IqraSpace Quran (Flutter) apps/flutter

The native Android (and web-capable) counterpart to apps/quran, but a fully separate codebase and data source: Tajweed-colored reading, Listening Mode, Supplications, bookmarks — all offline-first via Hive. Distributed through Google Play (closed testing).

Landing apps/landing

A single static HTML page that owns the iqraspace.org domain root and transparently proxies /quran/* and /learning/* to the other two Vercel projects. No framework, no build step, by design.

2High-Level Architecture

How a request actually gets from a browser to the right app, and how the four apps relate to each other.

Diagram

One connection root CLAUDE.md doesn't mention The R2 audio bucket is documented as apps/flutter's "one deliberate exception" to isolation from apps/quran. In the current code, apps/quran also fetches whole-Surah audio directly from that same bucket (its Listening Mode CSP allow-lists https://audio.iqraspace.org, and src/lib/content/listeningAudio.ts builds the same URL scheme, ported from the Flutter app's Dart constants). Nothing is shared code-wise or via imports — both apps independently hard-code URLs to the same public, keyless CDN endpoint — but it means the R2 bucket is now a dependency of two apps, not one. Worth knowing before renaming keys or restructuring that bucket.

Multi-Zones routing, traced end to end

A request to iqraspace.org/quran/some-page:

  1. DNS for iqraspace.org resolves to the apps/landing Vercel project (kept DNS-only/un-proxied on Cloudflare — see apps/quran's DEPLOYMENT.md).
  2. Landing's vercel.json evaluates its rewrites array. /quran/:path* matches a rule that transparently proxies to https://iqraspace-quran.vercel.app/quran/:path* — the browser's address bar never changes.
  3. That target is apps/quran's own, separately deployed Vercel project. Its next.config.ts sets basePath from NEXT_BASE_PATH, which is set to /quran only in that project's Vercel production environment — so the app's own routing lines up exactly with the incoming path. Bare / 404s on that project by design.
  4. The exact same pattern applies to /learning/* → https://iqraspace.vercel.app/learning/:path* (apps/learning's own project, own NEXT_BASE_PATH=/learning, plus explicit redirects() for old bare bookmarked paths).
  5. Anything not matching /quran* or /learning* is served directly by apps/landing (its own static pages), with landing's own security headers applied only there (scoped via a negative-lookahead source so they don't collide with the proxied apps' own headers).

Net effect: three fully independent Vercel projects/deployments, each with its own CI workflow and secrets, stitched into one apparent domain purely by an edge-level rewrite. There is no shared runtime and no monorepo-aware Vercel configuration.

5For a New Developer

A concrete, ordered path using only commands that actually exist in this repo.

  1. Read this document's §2–§4, then skim the per-app section (§6–§9) for whichever app you'll actually touch.
  2. Prerequisites: Node ≥20.9 + npm for the two Next.js apps; Flutter 3.47.3/Dart ≥3.5 for apps/flutter; nothing extra for apps/landing.
  3. Clone and install only what you need — there's no repo-wide install step: 
    # apps/learning
npm install --prefix apps/learning

# apps/quran
cd apps/quran && npm install

# apps/flutter
cd apps/flutter && flutter pub get
  4. Configure environment — copy each app's .env.local.example to .env.local and fill in your own Supabase project URL/anon key (learning) or Quran Foundation sandbox credentials (quran, only needed if you're touching content sync). apps/flutter needs no env file for normal development (only for the release-upload pipeline).
  5. Apply the DB schema (apps/learning only, if you need a working backend): 
    npx supabase login
npx supabase link --project-ref <your-project-ref>
npx supabase db push          # applies supabase/migrations/*.sql from repo root
    Or paste supabase/migrations/0001_init_schema.sql into the Supabase SQL editor as a one-time bootstrap, then push the rest.
  6. Run it: 
    npm run dev --prefix apps/learning   # http://localhost:3000
cd apps/quran && npm run dev          # http://localhost:3001 (deliberately different port)
cd apps/flutter && flutter run -d chrome   # or a connected Android device
  7. Verify: apps/learning — sign up, confirm a public.users/tutors or students row was created by the DB trigger. apps/quran — reading/search/bookmarks should all work with zero configuration (it's local-storage-only today). apps/flutter — the app should boot straight to Home with no login screen.
  8. Run the checks before any change: npm run lint, then npx next typegen && npm run typecheck (both Next.js apps need the next typegen step first on a fresh checkout — see §17), npm run build. For Flutter: flutter analyze and flutter test (what CI actually gates on).
  9. Make a small, safe change — e.g. a copy tweak in one component — and confirm the dev server hot-reloads it and lint/typecheck still pass.
  10. Understand deployment before pushing to main on anything CI-guarded (§16) — each app deploys independently on push to main (Flutter is analyze/test-only, no auto-deploy; release is a separate manual/skill-driven process, §16).

7apps/quran — IqraSpace Quran (public reader)

Free, anonymous-first Quran reader. The most actively developed app in the repo right now — most of its documentation (dated 2026-08-31) is 3+ weeks and 15+ commits behind the code.

Correcting a stale claim in root CLAUDE.md Root CLAUDE.md describes this app as "Next.js 16 + Capacitor" with cap:sync/cap:open:android scripts and a ci-quran-mobile.yml workflow. None of that exists in the current tree. package.json has zero Capacitor dependencies, there's no capacitor.config, no android/ folder, and .github/workflows/ only has four files (ci.yml, ci-quran.yml, ci-flutter.yml, ci-landing.yml) — ci-quran-mobile.yml exists only on the separate mobile/android git branch and was deliberately excluded when that branch's work was folded into main (merge commit 144d049: "main's apps/quran has since had its own newer redesign ... reconciling those two independently-evolved UIs is a separate, deliberate product decision"). The actual native Android app for the Quran reader today is the sibling apps/flutter, a fully different codebase.

Routes

/, /surah + /surah/[surahNumber], /page + /page/[pageNumber], /bookmarks, /search, /supplications + /supplications/[categoryId]. No /juz route — Juz Mode was deliberately removed (commit 1956544, replaced by per-Surah PDF Mode); several of this app's own docs (PRODUCT-ROADMAP.md, PROJECT-STATUS.md) still describe it as built — it is not, in the current tree.

Content pipeline

Source: Quran Foundation Content API (OAuth2 client-credentials, server-side only). npm run sync:content is a manual, developer-run step — not part of CI or the build — that fetches all 114 chapters / 6,236 verses (Uthmani text) plus translations and writes them to src/content/generated/. This output is deliberately committed to git, not gitignored (so CI/Vercel never needs live API access, and to respect the API's rate limits) — must be re-synced at least every 7 days per the Quran Foundation's license terms on cached content. A second, build-time-only pipeline (generate-search-index.mjs, wired into npm run build) turns that committed content into public/search-index.json for client-side search — no network call, no credentials needed at build time.

Cost-consciousness (hard constraint)

Target is genuinely $0/month at pilot scale: Vercel Hobby, Supabase free tier (currently idle), Quran Foundation API is free, and all audio streams from external CDNs (cdn.islamic.network for per-ayah, the Flutter app's Cloudflare R2 bucket for whole-Surah) — never through this app's own bandwidth. Explicitly disallowed absent a documented requirement: Kubernetes/microservices, Elasticsearch/Algolia, paid CMS, Redis, self-hosted audio storage. Search's static-JSON approach is a direct product of this rule, not a limitation to "fix" later.

Testing

None — no test script, no test framework, no test files. CI's test step is a documented no-op. A one-off manual accessibility pass (axe-core + Playwright, dev dependencies installed with --no-save and removed afterward) found and fixed two real bugs, but left no standing suite.

This app's own docs are stale PROJECT-STATUS.md, PRODUCT-ROADMAP.md, ARCHITECTURE.md, COST.md, and QURAN-CONTENT.md are all dated 2026-08-31 and still refer to the tutoring app by its old name (apps/web, renamed to apps/learning on 2026-08-31). They predate PDF Mode, the Juz-Mode removal, and the entire Flutter-parity feature set (audio, Reader Modes, Tajweed, search, Supplications, i18n) — treat their "not yet built" claims as historical snapshots, not a current inventory, and verify against code before relying on them.

8apps/flutter — IqraSpace Quran (native)

The Android (and web-capable) counterpart to apps/quran — a deliberately separate codebase and data source. Currently the most active part of the whole repo.

Architecture

Feature-first under lib/: core/ (audio, constants, network, storage, theme, widgets — shared infra) and features/{home, quran_reader, bookmarks, search, settings, supplications}, each with its own data/{datasources,models,repositories} → domain/{entities,repositories,usecases} → presentation/{providers,screens,widgets} layering (clean-architecture-lite). State management is Riverpod throughout, no codegen — plain Provider/FutureProvider/StateNotifierProvider. A recurring pattern: a StateNotifier reads its initial value from Hive on construction and writes back to Hive on every mutation, so Riverpod state and on-disk persistence never drift apart.

Local storage (Hive)

BoxContents
surah_cacheJSON-encoded, already Tajweed-parsed ayah lists per Surah — offline-first content cache.
reader_settingsTheme, font size, translation toggle, Tajweed on/off, reciter, reader mode, listening track, and the Supplications transliteration-script choice.
bookmarksBookmarked ayahs.
audio_file_cacheListening Mode's on-device audio cache metadata (Android only; web streams live every time).

No account/personal data is ever stored or transmitted — everything is local, confirmed both by the Play Data-Safety review and by there being no auth code at all.

Data source

Al Quran Cloud (api.alquran.cloud, keyless) is primary; a second client hits api.quran.com only for the Roman-Urdu translation (short timeout, failure silently swallowed — a "nice to have"). Once a Surah is fetched and Tajweed-parsed, it's served from Hive on every later open with no further network call.

Supplications feature (new)

A full vertical slice added alongside apps/quran's own port of the same feature: assets/supplications.json ("Hisn al-Qalb") currently has 25 of an eventual ~132 categories / 106 of ~267 duas populated — a deliberate, tracked content gap, not a bug (the data's own coverage_note says so). Each dua carries Arabic, three transliteration scripts (Latin/Telugu/Urdu — note the "Urdu" field is actually Arabic script reused, per the data's own sources_note), and an English translation. Three new Noto font families (Naskh Arabic, Nastaliq Urdu, Sans Telugu — SIL OFL licensed) render this content; the script choice is a single, Hive-persisted, app-wide setting. This feature replaced the bottom nav's previous "Learn — coming soon" placeholder slot (that screen and its test were deleted in the same change).

Listening Mode / Cloudflare R2

Plays one long-lived whole-Surah audio file (Al-Afasy recitation, or an Arabic+Urdu interleaved track — mutually exclusive, never both) rather than chaining per-ayah fetches, because the chained approach broke under Android's background/doze throttling. This is the app's first and only backend dependency, and the one deliberate exception to isolation from apps/quran: a dedicated Cloudflare R2 bucket (audio.iqraspace.org), chosen over Supabase Storage for no per-object size cap and no egress fees. Lock-screen/notification controls (audio_service) are wired only for this path — per-ayah playback stays in-app-only and pauses when the screen isn't active.

i18n

Three locales — English (template), Telugu, Urdu — declared in l10n.yaml, generated via flutter gen-l10n from .arb files (240 keys, kept in sync across all three). apps/quran reuses this wording verbatim wherever concepts overlap, to avoid divergent copy between the two Quran-reader surfaces.

Testing & release

  • CI (ci-flutter.yml): triggers only on the mobile/android branch (not main), path-filtered to apps/flutter/**. Runs flutter pub get → flutter analyze → flutter test only — no build/deploy job exists in CI.

Live-teach highlight sync (apps/learning), traced end to end

This is the most architecturally interesting workflow in the repo — a genuine real-time feature, not a demo.

  1. Tutor opens /teach/[lessonId] → TeachClient.tsx selects a PDF page or ayah.
  2. It broadcasts a "highlight" event with a HighlightState payload over a Supabase Realtime channel named lesson:{lessonId}.
  3. In parallel, it calls lib/sharing.ts's recordHighlight(), which durably writes the same state to the highlighted_content table — this is the architecture's audit trail, independent of the broadcast.
  4. The student's ShareClient.tsx (on /share/[lessonId]) is subscribed to the same channel and updates its view live on receipt. Both sides also use Realtime Presence (channel.track(...)) to show a "connected" indicator.
  5. Because broadcast has no replay, a reloading or late-joining student would otherwise see nothing until the next broadcast — getLatestHighlight() runs a DB catch-up query against the active sharing_sessions row on page load to fix that.

Net pattern: broadcast for liveness, database row for the record — a pattern worth reusing if a similar live-sync feature is ever needed elsewhere.

Notifications (apps/learning)

Plain DB rows, not push/email. All inserts go through a single notify_user() SECURITY DEFINER RPC — direct table inserts are never used — which only allows self-notify or a tutor notifying their own student. The topbar bell reads via a fetch wrapper; its exact refresh mechanism (poll vs. live) was not independently confirmed during this review — check NotificationBell.tsx directly before assuming it's real-time.

The documented local Android-emulator dev loop (TESTING.md) is the main way to reproduce device-specific bugs (notifications, lock-screen audio controls, background throttling) since these don't show up on web/desktop runs.
  • CI failures — check the specific workflow's Actions run; each job's step names map directly to the table in §16 (e.g. a failure at "Type check" almost always means the next typegen step didn't run first, or a real type error).

20Development Rules & Conventions

  • Apps are independent — verify before assuming sharing. No shared package, types, or UI library exists between any two apps. Cross-app references are always either a deep link (URL) or a duplicated file kept in parity by convention (e.g. Supplications JSON), never a code import.
  • apps/quran must stay anonymous-first. Reading, search, audio, and theme/font preferences must never require sign-in. Auth is reserved exclusively for future optional cross-device sync.
  • apps/quran's cost ceiling is a hard constraint, not a suggestion — no paid infra, no unnecessary third-party API dependencies for core reading. The resilience rule is explicit: "reading still works if audio/search/login/analytics are down."
  • apps/flutter's isolation from apps/quran is deliberate (different applicationId, no shared code) with exactly one sanctioned exception: the Cloudflare R2 audio bucket, which — per current code — both apps now independently consume (see the callout in §2). Don't casually add a second "exception."
  • RLS is the real authorization boundary in apps/learning, not client-side checks. Any new table needs its own RLS policies (migration 0001's tables shipped with RLS enabled but zero policies — a deliberate deny-by-default placeholder pattern to follow for new tables too).
  • Never reference another RLS-protected table via an inline subquery in a new policy — use or extend the existing STABLE SECURITY DEFINER helper functions to avoid the recursion bug fixed in migration 0004.
  • Admin/super_admin accounts are never created by public signup, by design, enforced server-side in the DB trigger and independently in the Edge Function. Don't add a code path that lets a client specify its own privileged role.
  • Quran content in apps/quran is licensed, cached content — it must be re-synced within the license's cache window (7 days) and must never be modified or redistributed as a standalone product. Don't hand-edit src/content/generated/.
  • Always bump only the +N build number in apps/flutter's pubspec.yaml before a real release build; bump x.y.z itself only for an explicit, user-requested version change.
  • Run app-specific commands from inside that app's directory (or with an explicit --prefix) — root package.json only proxies a subset of commands for two of the four apps.
