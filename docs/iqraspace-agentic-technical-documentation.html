1Executive Summary

What IqraSpace is, in plain terms.

Business Explanation

IqraSpace is a small, self-funded Islamic education brand with two distinct product lines under one name and one website:

  1. A free public Quran reader — anyone in the world can open iqraspace.org/quran or the Android app and read, listen to, and search the Quran with no sign-up, no ads, and no cost. This is the "give freely" side of the brand — a Sadaqah Jariyah (ongoing charity), not a commercial product.
  2. A paid-adjacent tutoring product — iqraspace.org/learning is a private classroom system for one solo Quran tutor and their students: scheduling lessons, teaching live with a shared PDF and synchronized highlighting, tracking attendance and progress, and keeping a shared curriculum.

These two products deliberately share nothing technical — different databases, different login systems, different codebases — because they serve different audiences with different privacy needs (the tutoring app holds real student data; the reader app is anonymous by design). A third, native Android version of the reader exists separately for the Play Store, and a single plain webpage ties all of it together under the iqraspace.org domain.

Guiding principles that shape every technical decision

  • The Quran reader must stay free and account-free forever. Reading, search, audio, and preferences never require login — this is a product promise, not just a current state.
  • The Quran reader must stay near-$0 to run. No paid databases, no paid search engines, no self-hosted media bandwidth for content that can stream from a free CDN instead.
  • The tutoring app protects real people's data. Minors' information (names, schedules, progress) lives only in its own access-controlled database, never touched by the public reader apps.
  • Each app can be rebuilt, redeployed, or even discontinued independently — none of the four apps' failure or removal breaks another.

2System Architecture

How a browser request actually finds its way to the right app.

Business Explanation

Think of iqraspace.org as a building lobby with a directory sign. The lobby itself (apps/landing) is a single, simple page. Walk toward "Quran Reader" or "Learning Portal" and the sign silently redirects you into a completely separate building (a separate deployed application, on a separate server, built by a separate team process) — but the elevator ride is seamless, so as a visitor you never notice you changed buildings. This means the tutoring app's ups and downs never affect the Quran reader, and vice versa.

One connection this repo's own top-level docs don't mention The Cloudflare R2 audio bucket is documented as apps/mobile/android's "one deliberate exception" to its isolation from apps/quran. Multi-Zones routing, traced end to end

A request to iqraspace.org/quran/some-page:

  1. DNS for iqraspace.org resolves to the apps/landing Vercel project (kept DNS-only/un-proxied on Cloudflare).
  2. Landing's vercel.json evaluates its rewrites array. /quran/:path* matches a rule that transparently proxies to https://iqraspace-quran.vercel.app/quran/:path* — the browser's address bar never changes.
  3. That target is apps/quran's own, separately deployed Vercel project. Its next.config.ts sets basePath from NEXT_BASE_PATH, set to /quran only in that project's Vercel production environment — so the app's own routing lines up exactly with the incoming path.
  4. The same pattern applies to /learning/* → apps/learning's own project.
  5. Anything not matching /quran* or /learning* is served directly by apps/landing, with its own security headers applied only there (scoped via a negative-lookahead source pattern so they don't collide with the proxied apps' own headers).

Net effect: three fully independent Vercel projects/deployments, each with its own CI workflow and secrets, stitched into one apparent domain purely by an edge-level rewrite. There is no shared runtime.

3The Four Applications

Independent products, one brand, one domain.

Quranic Teacher apps/learning

A tutoring LMS for one solo Quran tutor and their students: scheduling, live PDF-based teaching with real-time highlight sync, attendance, progress tracking, curriculum ("lesson plans"), notifications. Requires login. Lives at iqraspace.org/learning.

IqraSpace Quran apps/quran

A free, anonymous-first public Quran reader: Surah/Page/PDF reading modes, per-ayah and whole-Surah audio, Tajweed coloring, search, Supplications, bookmarks — all local-only today, no login required. Lives at iqraspace.org/quran.

IqraSpace Quran (Flutter) apps/mobile/android

The native Android (and web-capable) counterpart to apps/quran — a fully separate codebase and data source: Tajweed-colored reading, Listening Mode, Supplications, bookmarks, all offline-first via Hive. Distributed through Google Play (closed testing).

Landing apps/landing

A single static HTML page that owns the iqraspace.org domain root and transparently proxies /quran/* and /learning/* to the other two Vercel projects. No framework, no build step, by design.

Business Explanation

Why keep them so separate instead of one big app? Two reasons a business stakeholder would care about: trust and survivability. Trust — the tutoring app holds real students' (often minors') personal data behind a login; the reader apps hold nobody's data and need none, which is exactly the promise made to anonymous readers. Mixing the two systems would put children's data one bug away from public exposure. Survivability — because the four apps don't share code, a bug or outage in one cannot take down another. The Quran reader staying up doesn't depend on the tutoring database being healthy, and vice versa.

6apps/learning — Quranic Teacher (LMS)

A tutoring LMS for a single solo tutor and their students.

Business Explanation

This is the tutor's digital classroom. Instead of juggling WhatsApp for scheduling, a separate video call for teaching, and memory for tracking each student's progress, the tutor does all three from one login: book a session, open it and share a Quran page live with synchronized highlighting so the student sees exactly what the tutor is pointing at, mark who attended, record a skill score, and the student can log in separately to see their own schedule and progress. Every student's data is walled off from every other student and completely invisible to the public Quran reader apps.

Purpose
Mint short-lived, scoped presigned R2 URLs so the browser can upload/download/list/delete lesson materials without ever holding an R2 secret key — R2 has no RLS equivalent, so this function re-implements the exact access rules migrations 0011/0018 used to enforce directly on storage.objects.

7apps/quran — IqraSpace Quran (public reader)

Free, anonymous-first Quran reader — the most actively developed app in the repo.

This is the free gift to the public. Anyone anywhere can open the website, immediately start reading any of the 114 chapters, listen to a reciter, search for a verse, or read short daily supplications — with no sign-up wall, no ads, and no tracking of who they are. Follow-up (same review period): production incident + Supabase Storage → Cloudflare R2 migration

After the cleanup above shipped, iqraspace.org/learning/login stopped working in production. Traced live (headless-browser network capture, cross-checked against two independent public DNS resolvers) to the Supabase project itself being unreachable — pqlrexhtwgleokyiamie.supabase.co returned NXDOMAIN. Not a code or deployment regression: nothing in this repo can delete a Supabase project's DNS record. The Management API confirmed the project as INACTIVE (paused, not deleted) — the project owner restored it from the Supabase Dashboard, confirmed independently afterward (DNS resolved, Management API reported ACTIVE_HEALTHY, and the live login page's network calls succeeded with zero errors).

Business Explanation

A free-tier cloud database was automatically paused after a period of inactivity — the same way a free trial might lapse — which took the tutoring portal's login down until the owner clicked "restore" in the Supabase dashboard. Nothing was lost; it was a pause, not a deletion. That incident was also the trigger for a deliberate follow-up decision: move file storage (lesson material PDFs) off Supabase entirely and onto Cloudflare R2, so file storage no longer shares fate with the database/auth pause risk, and to match the (near-$0) cost model already used for apps/mobile/android's audio.

With Supabase reachable again, lesson-material file storage was migrated from Supabase Storage to a new, dedicated, private Cloudflare R2 bucket (iqraspace-learning) — full detail in §7's lesson-materials-r2 Edge Function write-up and §17/§18's updated data-architecture and integrations tables. Summary:

  • New Edge Function lesson-materials-r2 (presigned-URL broker) — R2 has no RLS equivalent, so this re-implements the exact access rules that used to live directly on storage.objects (migrations 0011/0018): own-folder write, admin bypass, any-authenticated read.
  • apps/learning/src/lib/storage.ts rewritten to call the broker — all 6 existing call sites needed zero changes.
  • All 4 existing files (15.5MB) copied from Supabase Storage to R2 via a one-off, resumable migration script — zero failures.
  • A real bug caught during testing, not a hypothetical: the R2 bucket needed an explicit CORS policy configured before the browser could PUT/GET against presigned URLs — Supabase Storage had handled this transparently, R2 does not.
  • Verified end-to-end against the live production Supabase project and R2 bucket through the actual UI: signed up a throwaway test account, uploaded a PDF, viewed it (rendered correctly via presigned GET), deleted it (confirmed gone on reload) — full CRUD, not just an API check. Test account and data cleaned up afterward.
  • Leftover removal (explicitly requested as a follow-up, not bundled automatically): migration 0024 dropped the 7 now-unused RLS policies from 0011/0018; a second one-off script removed the bucket's remaining objects and the bucket itself via the Storage API (Supabase blocks direct SQL DELETE on storage.objects/storage.buckets — "Use the Storage API instead"). Confirmed gone: the bucket now 404s. public.lesson_materials (the Postgres metadata table) was untouched throughout — only the Storage product's bucket/objects/policies were removed.

apps/learning's Supabase project is now scoped to exactly Postgres + Auth + Realtime + 2 Edge Functions — no Storage product usage at all. Its Google Drive integration (§6, still code-complete but undeployed) is unrelated and unaffected.

22Glossary

Every technical term used in this document, defined in plain English.

SSG (Static Site Generation)
Pages are fully built into plain HTML files ahead of time (at deploy time), not generated fresh for each visitor. Fast and cheap to serve; used throughout apps/quran (759 pages).
App Router
Next.js's file-system-based routing convention, where a folder path under src/app/ becomes a URL path and a page.tsx file inside it is that page's content.
Server Component
A React component that runs only on the server (or at build time) and never ships its own code to the browser — used for anything that reads files or a database directly.
RLS (Row-Level Security)
A Postgres database feature that filters which rows a query can see/edit based on who's asking — the real security boundary in apps/learning, not the app's own code.
SECURITY DEFINER function
A database function that runs with the permissions of the person who created it, not the person calling it — used carefully here to let a normal user safely trigger a privileged action (like sending a notification) without giving them broad table access.
Multi-Zones
A Next.js pattern for making several independently-deployed applications appear as one website by routing different URL paths to different backends at the edge (see §2, §10).
basePath
A Next.js setting that prefixes every route in an app with a fixed segment (e.g. /quran) so its internal routing lines up with where Multi-Zones proxies it to.
Edge Function
A small, independently-deployed backend function (here, on Supabase) for logic too sensitive to run in the browser — e.g. deleting a user account.
OAuth2 client-credentials
An authentication flow for server-to-server calls with no human login involved — used by apps/quran's content sync script to authenticate to the Quran Foundation API.
CDN (Content Delivery Network)
A network of servers that host and stream files (like audio) from a location close to the visitor, so the app itself never has to serve that heavy file traffic.
Realtime channel
A live, two-way connection (via Supabase Realtime) that instantly pushes an event from one connected browser to another — the mechanism behind live highlight-sync in apps/learning.
Hive
A lightweight, on-device key-value database used by the Flutter app (apps/mobile/android) to store everything locally — no server, no account needed.
Riverpod
The state-management library apps/mobile/android uses to keep its UI in sync with underlying data (similar in spirit to React's own state, but for Flutter).
Tajweed
The set of rules governing correct Quranic recitation pronunciation. "Tajweed coloring" means displaying Arabic text with each rule's affected letters shown in a distinct color.
Capacitor
A framework for wrapping a web app into a native mobile app shell. Referenced by some older docs for apps/quran, but not present on the current main branch (§21) — apps/mobile/android is the real native app today.
Dead code / orphaned file
Code that exists in the repository but is never actually called or imported by anything else — safe to remove once confirmed, since deleting it changes nothing a user would experience.
CI/CD
Continuous Integration / Continuous Deployment — the automated pipeline (GitHub Actions here) that checks and then publishes code changes without a human manually running each step.
Vercel
The hosting platform all three web-facing apps (learning, quran, landing) deploy to — each as its own separate, independently-billed project.
Anonymous-first
A product design principle meaning a feature must work fully without the user creating an account or signing in — apps/quran's core, non-negotiable rule.
