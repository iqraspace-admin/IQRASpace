# Duas — remotely managed content (schema, migration, admin, app)

> **Current deployment: the Learning app's Supabase project + admin area.** The Duas tables live in
> the Learning project (migrations `supabase/migrations/0025_duas_schema.sql` and
> `0026_duas_seed.sql` at the repo root, generated by `make_learning_migrations.mjs`) and are managed at
> **`/learning/admin/duas`** by users whose `public.users.role` is `admin` or `super_admin`. The
> standalone `apps/site/admin` page (since removed) and the `sql/0002|0003` files here (kept out of apps/site/supabase/migrations on purpose) are the
> earlier stand-alone variant (own staff table); they are not used with the Learning deployment.

Dua content used to live only in the Flutter app's bundled `assets/supplications.json`, so fixing a
single letter needed a Google Play release. It now lives in Supabase; an admin edits it in the
Learning admin area; the app downloads the **published** snapshot, caches it, and falls back to a bundled copy.

```
Learning admin (/learning/admin/duas) ──► Learning Supabase ──► get_dua_content() RPC (anon, published only)
                                                                        │
                                       Flutter: DuaRepository ◄── RemoteDataSource (dio) ── LocalCache (Hive) ── bundled asset
```

Nothing in Learning's existing tables (students, lessons, ...) is read or changed by the Duas tables.
The anon key the app uses is the Learning project's public key; the app can call only the two
published-only RPCs, never a table.

## Data model (one canonical Dua, many categories)

* `duas` — one row per canonical Dua: `slug` (unique canonical id), `title`, `arabic`,
  `transliteration_latin/telugu/urdu`, `translation_en`, `translation_ur`, `description`,
  `repeat_count` (integer — never in free text), `source_type` (`quran|hadith|mixed|other`),
  `source_collection`, `source_reference` (display string), `hadith_number`, `hadith_grade`,
  `quran_refs` (`[{surah, ayah_from, ayah_to}]`), `audio_url`, `status`
  (`draft|review|published|archived`), `verification_status` (`verified|unchecked|needs_review`),
  `review_notes`, `origin` (`iqs|wyn_public_pdf|wyn_revised_edition|independent`), `wyn_ids`,
  timestamps and `created_by/updated_by/published_at`.
* `dua_categories` — name (+ur/te), description, `sort_order`, `is_active`.
* `dua_category_map` — links a Dua to a category with `sort_order` and optional per-category
  overrides (`context_title`, `context_title_ur`, `context_note`, `context_reference`,
  `context_repeat_count`). This is how e.g. Ayat al-Kursi is one record shown under both *Evening*
  and *Before sleeping* with each context's own heading/virtue text/reference.
* `dua_audit_log` — append-only: every insert/update/delete of the three tables with full old and
  new row and the changed fields.
* Access: Learning's `public.users.role` (`admin`/`super_admin`) — no separate staff table in the Learning deployment.

Constraints worth knowing: published/review Duas must have Arabic; Arabic must be Arabic script (a
translation can't replace it); published Duas need an English translation; `repeat_count` 1–1000;
`audio_url` must be https; duplicates are caught by `slug` (hard) and `arabic_normalized`
(admin UI warning).

## Migration from `supplications.json`

Run from this folder (offline except `fetch_sources`): 

```bash
npm install                 # dev deps for tests only
node fetch_sources.mjs      # refresh verified source texts (needs network)
node build_canonical.mjs --write-bundled
npm test
```

What it does (see `reports/migration_report.md` for the actual numbers):

1. Imports all 106 legacy entries. Each keeps its exact **legacy position** as the mapping
   `sort_order`, so existing favourites (stored as category + index) still resolve.
2. Parses references into `source_type`/`source_collection`/`quran_refs`. It never invents hadith
   numbers or grades: `hadith_number` is filled only where the Wa Iyyaka research verified the
   reference against a hadith corpus *and* the Dua matched exactly.
3. Moves counts out of text into `repeat_count` where a whole-Dua count is stated; per-part counts
   (e.g. "3 times … 7 times" in one Dua) are left in the text and flagged for manual structuring.
4. Merges only identical Duas that sit in **different** categories (Ayat al-Kursi ×2, Three Quls ×2,
   Bismillah, A'udhu billah). Two identical entries in the *same* category (hajj#2/#3) can't share a
   record and are kept and flagged.
5. Applies the verified corrections (Istikhara from Bukhari 1166; Ayat al-Kursi and the three Quls
   from the Quran dataset).
6. Applies the Wa Iyyaka reconciliation: new categories, category mappings for "same Dua, other
   category", and **draft stubs** for entries genuinely missing from IqraSpace.
7. Generates `0003_duas_seed.sql` (idempotent, never overwrites admin edits) and the bundled snapshot.

### About the Wa Iyyaka content (important)

The book is copyrighted and the research inventory deliberately holds no Arabic or translation from it.
So the missing entries are **draft stubs with no Arabic** (title, reference, repetition, category,
`needs_review`) — except 9 Qur'anic ones whose Arabic/English come from the Quran dataset. Stubs are
never published automatically and cannot be (the DB refuses a published Dua without Arabic). An admin
must supply the Arabic from the cited hadith, verify it, add translation/transliteration, then publish.
Nothing is labelled "Wa Iyyaka" unless the inventory established the relationship (`wyn_ids`).
The old public-PDF edition is the only one audited; no revised-edition-specific entry could be
verified, so `wyn_revised_edition` is unused.

## Setup (owner, one time)

1. From the repo root (the Learning project is the linked one): `npx supabase db push` — applies
   `0025_duas_schema.sql` and `0026_duas_seed.sql` after the existing 0001–0024. (Alternatively paste
   those two files, in order, into Dashboard → SQL Editor. Run each once.)
2. Make sure you have an admin account in Learning (`npm run seed:admins` in `apps/learning`, or an
   existing admin/super_admin). Do **not** change Supabase's sign-up settings — Learning needs them.
   Only `public.users.role in ('admin','super_admin')` can touch Duas; students/tutors/guardians get nothing.
3. Sign in to Learning, open **Admin → Duas** (`/learning/admin/duas`).
4. Mobile: build with
   `--dart-define=DUAS_SUPABASE_URL=https://<learning-project-ref>.supabase.co --dart-define=DUAS_SUPABASE_ANON_KEY=<anon>`
   (the same public URL/anon key the Learning web app already uses). Without them the app runs on
   cache/bundled data.

## Editorial workflow

`draft → review → published` (and `archived`). Admins move a Dua through draft → review → published; they can also unpublish, archive and delete. (To correct a live Dua: edit it as admin — the history keeps the previous version —
or unpublish → edit → publish). The mobile app receives only `published` rows of active categories
(empty categories are omitted). Every change is in the **History** tab / Activity page with who/when/
before-after, and an admin can restore an earlier version.

## Mobile cache strategy

1. Show immediately from the last good cache (Hive), else the bundled asset — never blank.
2. If remote is configured and online: call `dua_content_version` (at most hourly, always on cold start,
   always on pull-to-refresh); if it differs from the cached version, fetch `get_dua_content`.
3. Validate (non-empty, every Dua has slug/title/Arabic-script Arabic). Only then replace the cache and
   refresh the UI. Any failure keeps the old cache. A corrupt or unknown-schema cache is ignored.
4. Favourites are keyed by Dua slug (legacy category+index favourites are migrated once through the
   bundled asset, which preserves legacy positions).

The bundled `assets/supplications.json` stays as the last-resort fallback and is regenerated by
`build_canonical.mjs --write-bundled`; it can be refreshed in any normal release but is never needed
for content corrections.

## Security model (verified by `tests/schema.test.mjs`)

* `anon` has **no table privileges**; its only entry points are `get_dua_content()` and
  `dua_content_version()` (SECURITY DEFINER, published rows only).
* Writes require a signed-in Learning user whose `public.users.role` is `admin` or `super_admin` (RLS + triggers); that column can only be changed via Learning's guarded `set_user_role()`.
* `dua_audit_log` cannot be written by any API role (audit rows come only from the
  trigger; deleting/updating them is denied outright).
* The service-role key is used by no client; only `api/contact.js` (server-side, unrelated) holds it.
* The admin UI is part of the Learning app (its auth and shell; Learning currently ships no CSP, only basic security headers); no separate admin site.

## Known gaps / NEEDS MANUAL VERIFICATION

See the final implementation report; in short: `translation_ur` is empty everywhere (no verified Urdu
translation exists in the source data and none was machine-generated); the English continuation and the
Latin transliterations for Istikhara, Ayat al-Kursi and the three Quls need a scholar's check; Telugu
transliteration for those three was removed rather than leave a partial text; 95 Wa Iyyaka drafts need
Arabic and verification; `hadith_number`/`hadith_grade` are empty for almost all legacy Duas (references
are collection names only); and `apps/site/duas.html` (the website's static Duas page) is **not** yet
driven by this database.
